# Bybit 200k Eval Bot — Build Plan

Companion to `STRATEGY.md` (research/validation) — this document tracks the live-bot build only.

**Key discovery informing this plan:** the uploaded `botcode.zip` already contains a partial live-trading skeleton — `bybit_client.py`, `compliance.py`, `main.py`, `shared_positions.py`, `config.py` — built for a firm called "HyroTrader" on a $200k account. Its account rules (10% profit target, 10% max drawdown, 5% daily drawdown, swing DD) exactly match the numbers `STRATEGY.md`'s backtests were built around ($200k start / $220k pass / $180k bust), so this is almost certainly the same account. Its `strategy.py`, however, is a completely different, older single-signal strategy (Supertrend + EMA(8/21) + ADX, 15 coins, max 2 concurrent positions) — unrelated to the validated 5-sleeve system (Main/Short/Flow + DELTA/RELVOL/BOS). **This plan reuses the exchange/compliance/execution skeleton and replaces the strategy brain entirely.**

## Phase 0 — Lock the spec — ☑ DONE
Goal: no ambiguity before a line of new code is written.

- ☑ Confirmed real challenge structure (user-clarified, corrects old `config.py`): Phase 1 (10% target) → account reviewed → Phase 2 (separate 5% target) → funded. Minimum trading days is 4 (not 10/5 as `config.py` stated) — non-binding, every median time-to-pass computed is well above this. 40% consistency rule explicitly waived by user — not modeled going forward.
- ☑ Ran the two-phase Monte Carlo (see `STRATEGY.md` §44): Phase 1 reproduces the existing §42/43 numbers exactly (98.63%/98.75% pass, ~46 day median) as a consistency check. Phase 2 (5% target, same risk params) gives 99.45%/99.53% pass, ~22 day median. **Chained fully-funded estimate: ≈98.1-98.3% probability, ≈68 median days total.** Flagged assumption carried forward: Phase 2 is modeled starting fresh from $200k with the same risk parameters as Phase 1 — the real carry-over/reset mechanics between phases are still unconfirmed and should be checked against the firm's actual Phase 2 terms.
- ☑ Position-model decision (user delegated "whichever is better for us"): **independent, additive sleeves — the model actually backtested in `STRATEGY.md`.** Reasoning: every pass-rate, Sharpe, and kill-switch number produced this session assumes sleeves size independently with gross exposure adding; switching to the existing code's first-claim exclusivity model would invalidate all of that validated work in exchange for an unbacktested, unknown-performance alternative. For the 10 coins both strategies can touch, opposite-signed orders will net automatically at the exchange (one-way/net margin mode) — same-signed orders from different sleeves in the same coin simply stack. `shared_positions.py`'s cross-bot exclusivity logic will be retired for this system, not reused.
- ☑ Frozen final parameters as the single source of truth: 5 sleeves (Main 5L/72h, Short 5S/7d, Flow 5L+5S/7d, DELTA 6L+6S/7d, RELVOL 6L+6S/7d, BOS ≤6S/event-driven), A-universe (25 coins) vs B-universe (27 coins, 10 shared), L=1.70, -$3,000 intraday kill switch, ORIG_THROTTLE drawdown bands, independent/additive position model, one-way exchange margin mode required.

## Phase 1 — Audit the existing skeleton — ☑ DONE
Goal: know exactly what's reusable vs. what must be rebuilt, before assuming either way.

Full findings in `AUDIT_FINDINGS.md`. Summary:

- ☑ `bybit_client.py` — solid core (Decimal quantization, order chunking, correct V5 endpoints). Gaps: no hedge-mode/`positionIdx` support (moot now — one-way mode chosen above), `TESTNET_URL` actually points to Bybit's Demo Trading domain not real testnet, no idempotency keys, no rate-limit handling, single-timeframe fetch only (no multi-timeframe orchestration yet needed for BOS's structure-break logic).
- ☑ `compliance.py` — static max-DD floor (90%/$180k) and daily swing floor ($10k) both match backtest assumptions. **Does not** implement the graduated ORIG_THROTTLE exposure cut every backtest number assumes (only a binary 85%/80% freeze) — must be rewritten, not extended. Has its own pre-existing $6,000 circuit breaker that conflicts with the new -$3,000 kill switch — will be replaced by the kill switch, not run alongside it.
- ☑ `main.py` — architecturally single-strategy (one engine, one coin list, one hourly cadence); needs restructuring to run 5 sleeves on 3 different cadences (72h/weekly/event-driven), not just a strategy-file swap. Reusable patterns: stop-loss-attached-within-deadline check, disk-persisted state with restart recovery, Discord alerting, exchange-position-sync-on-restart. `shared_positions.py`'s cross-bot exclusivity will not be reused (see Phase 0 decision above).
- ☑ `config.py` — leverage field (10x) is the exchange per-symbol margin setting, a different concept from the L=1.70 portfolio-level notional multiplier; needs an explicit translation layer so the two are never conflated when sizing live orders.

## Phase 2 — Build the signal engine — ☑ DONE
Goal: live signals that are provably identical to the backtested ones.

- ☑ Data ingestion — `signal_engine/data_loader.py` wraps the exact matrix-building functions from both reference files (`option1_reference.build_matrices()` for universe A / 25 coins, `reference_impl.build_matrices(select_universe())` for universe B / 27 coins), with `as_of_date` trimming so the same loader serves both historical parity testing and (once CSV reads are swapped for live ingestion in Phase 4) live use.
- ☑ Each sleeve implemented as its own module under `signal_engine/`, each REUSING the validated reference functions directly rather than reimplementing the math:
  - `sleeve_main.py` — wraps `option1_reference.sleeve_A` (momentum+carry), 5L/5S
  - `sleeve_flow.py` — wraps `option1_reference.sleeve_F` across all 3 lookbacks (2/3/5d), averaging the three INDEPENDENTLY-RANKED weight vectors (mathematically equivalent to the backtest's PNL-ensemble — documented in-file, including one known stateless-snapshot divergence on rare insufficient-valid-names days)
  - `sleeve_delta.py` / `sleeve_relvol.py` — wrap `reference_impl.sig_delta` / `sig_relvol`, 6L/6S
  - `sleeve_short.py` — wraps `sleeve_S_reconstructed.build_signals()` unchanged; inherits that file's own explicit "RECONSTRUCTED FROM PROSE, NOT VERIFIED" caveat (original `short_engine_backtest.py` was never found)
  - `sleeve_bos.py` — re-derives the exact regime/trigger/confirm state machine from `reference_impl.py`'s `_atr`/`_pivots`/`_load_4h` and constants to answer "is there a fresh signal at the latest confirmed bar" (a live-snapshot question `run_bos()`'s full backtest loop isn't structured to answer directly); one deliberate, documented divergence (state machine walks every bar rather than skipping bars covered by an open simulated trade — correct for decoupled live signal generation, flagged as untested by parity for that reason) and one real bug caught and fixed during build (stop/tp must be based on the actual entry price `o[i+1]`, not the trigger bar's close — an earlier draft had this wrong)
  - `rank_weights.py` — the shared top-N/bottom-N weight construction, copied verbatim from `run_sleeve()`'s own ranking lines
- ☑ Signal parity test (`signal_engine/parity_test.py`) — exact numeric results, not just pass/fail:
  - Main: 500/500 exact matches (5 seeds × 100 random historical days each), max abs diff 0.000e+00
  - Flow: 40/40 exact matches (1 seed × 40 days), max abs diff 0.000e+00
  - DELTA: 40/40 exact matches, max abs diff 0.000e+00
  - RELVOL: 40/40 exact matches, max abs diff 0.000e+00
  - Short: 25/25 coins (full universe A) — trigger flag matches independently-recomputed reference
  - BOS: 27/27 coins (full universe B) — trigger flag AND trend state match independently-recomputed reference
  - **Every sleeve: 100% exact match, zero mismatches, across every check run.**

## Phase 3 — Build the portfolio/risk layer
Goal: turn 6 independent signal streams into one sized, risk-controlled book.

- ☑ Position sizing — `portfolio_layer/` package built:
  - `sleeve_combiner.py` — Strategy A eq-thirds `(main+short+flow)/3`, exact match to `build_blend.py`, no look-ahead. Strategy B core/blend reproduces `reference_impl.py`'s structure (`core=(nz(delta)+nz(relvol))/2`, `blend=2/3*nz(core)+1/3*nz(bos)`) but with a **causal trailing-window substitute for `nz()`**.
  - **CRITICAL FINDING, not previously surfaced:** `reference_impl.py`'s `nz = lambda x: x/x.std()` normalizes using the **whole-sample (full-history, including future) standard deviation**. A live system cannot know future volatility — this exact function is impossible to reproduce live. The causal replacement (`_trailing_nz`, 30-day trailing std) is a **new, unvalidated design choice**, not a verified reproduction of the backtested Strategy B Sharpe (2.09 core / 2.38 blend, per `reference_impl.py`'s own docstring). It has NOT been separately backtested.
  - `ab_blend.py` — the causal 30-day trailing inverse-vol A/B blend (`inv_vol_weighted()`) copied verbatim from `dynamic_weight_test.py`. This step WAS already causal in the original backtest (walk-forward validated, W=30 fit on 1st half only) — verified bit-exact (0.0 max abs diff) against `/tmp/combo_invvol.npy`.
  - `position_sizer.py` / `portfolio.py` — derive final per-sleeve, per-coin dollar targets by algebraically expanding the nested combination into a scalar multiplier per sleeve (`m_main=wA/3`, `m_delta=(1-wA)/(3·vol_core·vol_delta)`, etc.), with an explicit (non-backtested) safety cap against divide-by-near-zero blowup.
  - **Validation (`validate_phase3.py`), exact numbers:**
    - Strategy A combiner vs `eq_thirds_ret.npy`: max abs diff = 0.0000000000e+00, exact match.
    - Strategy A combiner vs `/tmp/combo_a_correct.npy`: max abs diff = 2.4862e-04, NOT an exact match — a small, pre-existing discrepancy between two of the workspace's own cached "ground truth" files (consistent with the already-disclosed main-sleeve intraday-reconstruction reconciliation in `assemble_combined_hourly.py`), not something Phase 3 introduced. My code exactly reproduces the officially-defined artifact (`eq_thirds_ret.npy`, per `build_blend.py`'s own docstring).
    - `ab_blend.inv_vol_weighted()` vs `/tmp/combo_invvol.npy`: max abs diff = 0.0000000000e+00, exact match. Recomputed Sharpe 2.474982 = saved Sharpe 2.474982.
    - Strategy B combiner vs `/tmp/combo_b_correct.npy`: **now attempted, using real historical data — see next bullet for the new finding this surfaced.** Not an exact match; a genuine, previously-undiscovered reconstruction gap, not just the expected causal-vs-look-ahead difference.
  - Smoke test (`smoke_test.py`) also surfaced a real behavioral property worth flagging: with random synthetic sleeve data, the nested vol-scaling made wB collapse to ~0.0002 (wA≈0.9998) — the Strategy B construction is highly sensitive to the trailing vol estimates feeding it. This underscores why the causal `nz()` substitute needs real historical backtesting, not just a smoke test, before being trusted at scale.
  - **NEW CRITICAL FINDING (this segment) — undocumented vol-targeting rescale in Strategy B, and an unresolved reconstruction gap.** Backtested the causal `_trailing_nz()` substitution against `reference_impl.py`'s original look-ahead `nz()` using REAL historical data (`backtest_causal_b_v2.py`, running `select_universe()`/`build_matrices()`/`run_sleeve()`/`run_bos()` against the live `clean_panel` data — not synthetic). This surfaced two distinct issues:
    1. `combo_b_correct.npy` (the cached "ground truth" Strategy B series all of Phase 3's sizing depends on via the A/B blend) is **not** the raw `nz()`-based blend — it's that dimensionless blend **rescaled to a target daily vol of ~0.963%/day (~18.4% ann)**. This rescale step was **not written down anywhere in the workspace's code** before this pass. Fixed: `sleeve_combiner.strategy_b_combo()` now applies this rescale causally (trailing-window std, not whole-sample), and `position_sizer.py`'s algebraic multiplier derivation was updated with the corresponding `extra_factor` term. Both re-validated: `smoke_test.py` and `validate_phase3.py` pass with the updated code.
    2. Even after correcting for that rescale, reconstructing `combo_b_correct.npy` from the current `clean_panel` data under the exact look-ahead `nz()` formula gives only **corr=0.9862, R²=0.9725 — not an exact match**. The reconstructed series' Sharpe (**2.5895** on the correct 568-day window) is materially higher (~24% relative) than the real cached series' actual Sharpe (**2.0888**). This means `combo_b_correct.npy` embeds at least one more undisclosed difference (most likely a frozen/different data snapshot — live `clean_panel` has grown since the cache was built — or a different universe selection) that could **not** be tracked down this pass. `strategy_b_combo()`'s live behavior remains **unvalidated against the original backtest to full precision.**
    3. Head-to-head exact numbers on the properly-rescaled 568-day window: causal Sharpe **2.5749** vs reconstructed-look-ahead Sharpe **2.5895** (CAGR 68.68% vs 51.34%; MaxDD 9.65% vs 6.79%; ann vol 21.16% vs 16.52%) — a small (~0.6% relative) Sharpe gap between causal and look-ahead **within this reconstruction**, but causal runs hotter (higher CAGR, MaxDD, vol) for essentially the same risk-adjusted return. **This is NOT the same as "causal costs ~0% vs the real validated backtest"** — see point 2, the reconstruction itself already diverges materially from the real cached ground truth for reasons independent of causality. Substituting the causal-B reconstruction into the full A/B inverse-vol blend (paired with the real, validated `combo_a_correct.npy`) gives Sharpe 2.7256 vs the real cached blend's 2.4750 — this delta should **not** be read as "the causal fix improves the strategy"; it is very likely an artifact of the same unresolved reconstruction gap and is called out here explicitly so it is not mistaken for a genuine improvement.
    4. Walk-forward split of the causal reconstruction: 1st half Sharpe 3.3454, 2nd half Sharpe 1.7094 (real cached series shows the same shape: 2.5402 → 1.6017) — a real, pre-existing decay pattern in Strategy B, not introduced by the causal substitution, consistent with the standing rule that momentum-style signals are BTC-macro-regime dependent.
  - **Bottom line:** the causal normalization fix itself looks cheap on a relative basis (Sharpe -0.6%), but Strategy B's sizing module cannot currently be validated against the originally reported Sharpe 2.09/2.38 numbers with confidence, due to an independent, still-open data/reproducibility gap. Treat Strategy B position sizes as **provisional** until this gap is closed (either by locating the exact original generation script/data snapshot, or by re-deriving and re-validating `TARGET_DAILY_VOL` and the universe/data cutoff directly).
- ☑ Kill switch — `risk_overlay.py` implements the -$3,000 intraday flatten-and-block-reentry-until-next-session logic and the ORIG_THROTTLE drawdown bands (100%/50%/30% at 4%/8% trailing drawdown), reusing the exact thresholds from `mc_hourly_ks.py`, restructured as a live state tracker (`RiskState`). Smoke-tested: throttle band boundaries, kill-switch trip/reset across sessions, and drawdown-band transitions all behave as specified. NOT yet wired to a real live equity feed (no such feed exists yet — that's Phase 4/5 scope).
- ☑ Compliance wiring — `portfolio_layer/compliance.py` built: tracks LIVE account equity (not backtest equity) against HyroTrader's actual max-drawdown floor and daily-loss-limit rules, phase by phase, separate from `risk_overlay.py`'s own strategy-risk kill switch. Max-DD floor is modeled as a trailing, ratcheting floor (peak minus a fixed $ cushion = 10% of the phase's starting balance — matches the third-party source's own "floor rose to $X" numeric example). Daily loss floor = day-start equity − $10,000. Phase 1→2 transition applies the **confirmed** balance/target reset (STRATEGY.md §44a point 1).
  - **Explicit configuration flag for the still-UNRESOLVED drawdown-floor carry-over question (STRATEGY.md §44a point 2):** `DrawdownFloorMode.RESET` (default) vs `DrawdownFloorMode.CARRY_OVER`. Neither is confirmed; RESET is the more operationally plausible reading but is not independently verified either. Do not deploy Phase 2 compliance checks without first choosing this deliberately (ideally after confirming with HyroTrader support) — see `compliance.py`'s module docstring for full sourcing.
  - Tested (`test_compliance.py`) with a concrete scenario (Phase 1 peak $232,000, Phase 2 dip to $206,000): under RESET the floor is $180,000 (20,000 of room to spare, not busted); under CARRY_OVER the inherited floor is $212,000 (busted by $6,000 on an otherwise unremarkable 3% Phase-2 dip). Reproduces STRATEGY.md §44a's aggregate Monte Carlo finding with a concrete live-tracking example. All assertions pass.
  - NOT yet wired to a real live equity feed (same Phase 4/5 dependency as `risk_overlay.py`) and does not yet implement the 40% consistency rule (explicitly waived by the user per STRATEGY.md §44, not modeled).

## Phase 4 — Execution layer — ◐ IN PROGRESS (wiring built and smoke-tested; live path deliberately blocked)
Goal: signals become real orders, safely.

- ☑ Built the full bot package under `bot/`: `config.py`, `exchange_client.py` (`HardenedBybitClient`, extends the existing `bybit_client.py` — "the heart" — unchanged for all proven methods: `get_klines`, `get_ticker`, `get_instrument_info`, `get_wallet_balance`, `get_positions`, `set_leverage`, `quantize_qty`/`quantize_price`, `place_order_chunked`, `modify_sl`, `close_position`), `state.py` (`BotState`, atomic save/load with restart recovery), `alerts.py` (Discord webhook, fire-and-forget), `reconciliation.py` (exchange-vs-internal position reconciliation, orphans NOT auto-adopted), `sleeve_history.py` (feeds the 6 sleeves' historical return series into the portfolio sizer), `event_sleeves.py` (live Short/BOS event-driven slot trackers, `MAX_CONCURRENT=6`), `data_feed.py` (`ReplayDataFeed` for backtesting/dry-run against static CSVs, `LiveDataFeed` stub), `orchestrator.py` (`HyroTraderBot`, cadence-gates all 6 sleeves independently: Main 72h, Flow/DELTA/RELVOL 168h, Short/BOS 4h check interval), `main.py` (CLI entrypoint: `--dry-run` default, `--live`, `--cycles`, `--as-of`).
- ☑ **Extended to `HardenedBybitClient`, not just inherited:** exponential-backoff retries (`MAX_RETRIES=4`) wrapping `_get`/`_post`, idempotent `orderLinkId` on every order, explicit `ExchangeMode.{MAINNET,DEMO,TESTNET}` (the original `config.py`'s "testnet" URL was actually Bybit's Demo Trading domain `api-demo.bybit.com`, not the real testnet `api-testnet.bybit.com` — this is now made explicit, not silently reproduced), and `assert_one_way_mode()` which checks live `positionIdx` and raises rather than silently trading in the wrong margin mode (one-way mode is a hard requirement of the additive/independent sleeve position model chosen in Phase 0).
- ☑ **Real bug found and fixed via the smoke test (reporting per standing rule — do not silently patch):** first end-to-end dry run crashed with `ValueError: operands could not be broadcast together with shapes (1262,) (1302,)` inside `portfolio_layer/sleeve_combiner.py::strategy_a_combo()`. Root cause: `bot/sleeve_history.py`'s original `_short_history()` defaulted to `lookback_days=180`, which degenerated to `start=None, end=None` when called with `as_of_date=None` — returning the Short sleeve's **entire** available history (1302 daily rows, 2023-01-01 → 2026-07-25) instead of a window matching Main/Flow's own warmup-trimmed axis (1262 rows, 2023-02-10 → 2026-07-25; the 40-row gap is exactly `option1_reference.WARMUP=40`). **Fix:** `_short_history()` now always pulls the Short sleeve's full history, then explicitly `pandas.reindex()`s it onto the exact `main_dates` axis pulled from `_main_flow_histories()`, and raises a loud `ValueError` (not a silent pad/truncate) if any date is missing. Re-verified after the fix: main/short/flow all align at n=1262 exactly. Separately checked (no bug — false alarm) that DELTA/RELVOL/BOS histories were already correctly aligned at 884/884/884 rows each via `reference_impl.py`'s own consistent 45-day-warmup trimming.
- ☑ **Second bug found and fixed via the smoke test:** `orchestrator.py`'s cadence-gating loop only added a sleeve to `report["rebalanced_sleeves"]` when at least one sleeve was due (`report.setdefault(...).append(...)`), so on any cycle where **zero** sleeves were due, the key was missing entirely from the report dict instead of being an empty list. Fixed by initializing `report["rebalanced_sleeves"] = []` unconditionally before the gating loop.
- ☑ **Smoke test (`bot/smoke_test_bot.py`) — exact numbers, all assertions passed:**
  - Cycle 1 (fresh state, first-ever cycle): all 6 sleeves correctly rebalanced. `account_multiplier=1.700000`. Sleeve multipliers: main=flow=short=0.267415, delta=relvol=bos=0.001577, wA=0.802244, wB=0.197756, extra_factor=0.007976. **Gross notional = $146,367.47** across 34 nonzero-dollar positions (largest: BRETT −$12,122.80, LINK +$12,167.49, ZEC/AAVE ±$9,136.79). Compliance: equity=$200,000, max_dd_floor=$180,000, distance_to_floor=$20,000, not busted.
  - Cycle 2 (+2h, same process): correctly rebalanced **zero** sleeves (shortest cadence is Short/BOS at 4h) — dollar targets carried forward byte-for-byte identical to Cycle 1 (asserted exact dict equality, not just "close enough").
  - Cycle 3 (+5h, same process): correctly rebalanced exactly `['short', 'bos']` (4h cadence now due; Main/Flow/DELTA/RELVOL correctly still held).
  - **Restart-recovery test:** killed the process, instantiated a brand-new `HyroTraderBot` pointed at the same state file — `cycle_count` (3), every sleeve's `last_rebalance` timestamp, and `last_dollar_targets` all recovered exactly, byte-for-byte, with no reset or drift.
